voice-notion — 部署與選型架構說明書

一個把 Slack 語音／文字訊息轉成 Notion 頁面與任務、並每日自動統整站會的機器人；本文件說明它在 AWS 上的架構選型、每一項技術決策的原因、以及從初版到當前狀態的完整演進。

ECS Fargate · web + worker DynamoDB · SQS · EventBridge Rule Amazon Transcribe（STT） Bedrock Claude Opus 4.8（文字） region：ap-northeast-1 + us-east-1 task-def rev9

1摘要（TL;DR）

voice-notion 原本是單機 Next.js 服務（狀態放記憶體、背景工作 fire-and-forget）。為了在雲端能水平擴容、滾動更新不掉資料、符合金控資安基準，重構為以 ECS Fargate 為核心、佐以 DynamoDB / SQS / EventBridge 的雲原生架構，AI 能力全部改走 AWS 託管服務（無 OpenAI 依賴）。

3ECS / Fargate 與 web／worker（白話 + 設定）

「ECS」「Fargate」常被綁在一起講，但其實是兩個不同層級的東西；而「web／worker」是本專案的設計。本章用白話講清楚各是什麼、以及本專案怎麼設定（值取自 taskdef.json rev9）。

一句比喻：你要開餐廳出餐。ECS 是店長——決定幾個廚師上工、有人請假就補人、換菜單時怎麼無縫接手；Fargate 是廚房＋瓦斯爐——實際煮菜的地方，但你不用自己買爐、修爐、清爐。

ECS 與 Fargate：兩個層級

ECS編排 / 控制平面
本身不跑你的程式——負責「管理」：要跑幾份、掛了重啟、滾動更新、掛到 ALB
+
Fargate算力（Serverless Compute）
實際跑容器，你只說要多少 vCPU/記憶體，底層 VM／OS patch 全由 AWS 託管

ECS 也能搭配自管 EC2 當算力，本專案選 ECS + Fargate 以免管底層機器。

ECS 負責的四件事

職責具體意思
維持數量你說「1 個 task 常駐」，ECS 就維持 1 個；少了自動補
健康自癒container 崩潰 / task 死掉 → 自動拉新的起來
滾動更新出新版時先起新 task、健康後才關舊 task → 零停機
掛載 ALB告訴 ALB「流量往這個 task 的 IP:3000 送」

ECS 的名詞層層包起來

Cluster（叢集）邏輯群組，本專案 = voice-notion
▼
Service（服務）「維持 N 個 task 常駐」的規則 · 掛 ALB · 滾動更新
▼
Task（任務）依 Task Definition（藍圖/食譜）跑起來的實體 · 內含 1~N 個 container
▼
container: webnode server.js
container: workernode dist/worker.js

Task Definition 是範本（藍圖），Task 是照藍圖跑起來的實體

web 與 worker：同 image、不同角色

本專案一個 Fargate task 內跑兩個 container，用同一個 image，只靠啟動指令（command）不同扮演不同角色：

web ＝ 前門（快速應答） node server.js（Next.js）· 對外 :3000
收 Slack webhook / /api/health / /api/cron/standup
只做輕量事：驗簽 → 丟 SQS → 3 秒內回 200
（Slack 規定 3 秒沒回就當逾時重送，故 web 絕不自己做慢事）
worker ＝ 後廚（慢工出細活） node dist/worker.js · 不對外（無 port）
一直 long-poll SQS，撈到就做重活：
ffmpeg → Transcribe → Opus 4.8 → Notion
另每 30s 做草稿提醒 / 逾期清理

為什麼要拆成兩個？

問題拆開後
Slack 要 3 秒回，但轉錄要 30–120sweb 秒回、worker 慢慢做，互不阻塞

怎麼設定？Cluster → Task Definition → Service

① Cluster（一次性）

aws ecs create-cluster --cluster-name voice-notion

② Task Definition（藍圖）— 關鍵欄位

欄位意義本專案值

networkModeFargate 唯一支援；每 task 拿自己的私有 IPawsvpc
command同 image 靠這行區分 web/workerweb node server.js；worker node dist/worker.js

secrets從 SSM SecureString 注入，不寫死在 image8 個 /voice-notion/*

⚠️ cpu/memory 不能亂填——只能選 AWS 允許的組合：0.25 vCPU→0.5~2GB、0.5 vCPU→1~4GB、1 vCPU→2~8GB…。註冊指令：aws ecs register-task-definition --cli-input-json file://.deploy-tmp/taskdef.json，每次註冊產生新 revision（目前 rev9）。

③ Service（維持常駐 + 掛 ALB）

aws ecs create-service \
  --cluster voice-notion --service-name voice-notion \
  --task-definition voice-notion \
  --desired-count 1 \                          # 維持 1 個 task 常駐
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={
      subnets=[subnet-08f30e8fce56c45e2,subnet-02e0d8667a43f94c5],  # 私有子網雙 AZ
      securityGroups=[sg-02879faed4c21ad5b],
      assignPublicIp=DISABLED }" \             # 無 public IP（合規 ECS.2），出網走 NAT
  --load-balancers "targetGroupArn=<voice-notion-tg>,containerName=web,containerPort=3000" \
  --health-check-grace-period-seconds 60
設定意義
--desired-count 1Service 的核心職責：永遠維持 1 個健康 task，掛了自動補
...containerName=web只有 web container 接 ALB 流量（worker 不接）
assignPublicIp=DISABLED + 私有子網合規；task 出網（Bedrock/Notion/Slack）走 NAT gateway

④ 出新版（滾動更新，零停機）

# build + push 新 image → 註冊新 revision → 觸發滾動更新
aws ecs update-service --cluster voice-notion --service voice-notion \
  --task-definition voice-notion --force-new-deployment
零停機的原理：ECS 會先起新 task、確認健康後才關舊 task，全程都有 web 實例在接 Slack。ECS＝店長（管數量/自癒/更新/掛 ALB）、Fargate＝免管廚房（實際算力）、web＝前門（秒回 Slack）、worker＝後廚（從 SQS 撈工作慢慢做）。

4架構選型比較（候選架構）

性質說明：本節是選型脈絡的說明——比較當初評估過的運算平台候選，解釋為何最終落地為 ECS Fargate。實際部署即以 Fargate 完成（見第 5 章）。

核心需求塑造了選型——以下四項是評分各候選的標準：

(a) 3 秒回 200 入口

Slack webhook 必須在 3 秒內 ack，否則被判逾時重送。

(b) 常駐背景 worker

轉錄／LLM 需 30–120s，得有 long-poll SQS 的常駐消費者。

(c) 私有子網合規

金控資安基準要求 task 不得有 public IP。

(d) 掛既有 ALB

用 host-based rule 掛公司既有 ALB，不另建對外入口。

候選常駐 worker冷啟動 / ffmpegHA / 擴容維運成本私有子網 & 掛既有 ALB契合度
Lambda + API Gateway ✗15 分鐘上限、非常駐，long-poll worker 不自然 △冷啟動延遲；ffmpeg 需自打 layer ✓自動、極佳 ✓低 ✗接既有 ALB 需額外 target 設定，長工作彆扭 低
EC2 自管 ✓完全可 ✓可預裝 ffmpeg △要自建 ASG / 健檢 ✗高：自己 patch OS、管 AMI △可，但一切自理 中低
App Runner △單服務導向，web+worker 同 task 綁定不易 ✓容器化，OK ✓自動 ✓低 ✗私有子網 + host-rule + 雙容器彈性不足 中
ECS Fargate（採用） ✓worker 容器常駐 long-poll ✓image 內含 ffmpeg（node:20-slim） ✓調 desired count、滾動更新零停機 ✓低：免管 VM / OS patch ✓同一 task 雙容器、進私有子網、掛 aaron-dev TG 最高
結論：ECS Fargate 是唯一同時滿足「常駐 worker + 免管底層 + 雙容器同 task + 私有子網合規 + 掛既有 ALB」的選項。它其實是兩件事的組合：
Fargate算力（Compute）
實際跑容器，免管底層 VM / OS patch
+
ECS 控制平面編排（Orchestration）
跑幾個 task、掛了重啟、滾動更新

5當前架構逐元件原理

每個元件都回答兩個問題：它負責什麼、為何這樣選。

ECR

存 build 好的容器 image（web + worker 共用同一份）。以 git SHA / 時間戳當 tag，方便 rollback。

ECS 控制平面

決定跑幾個 task、掛了重啟、滾動更新。

Fargate 算力

實際跑容器，免管底層 VM／OS patch；跑在私有子網、無 public IP。

CloudWatch Logs

兩容器 stdout/stderr（logInfo/logError），stream prefix 分 web / worker。

web + worker：雙容器、同 image、不同 command

一個 Fargate task 內兩個 essential 容器共用同一 image：

  • web：node server.js（Next.js standalone），對外 3000，收 Slack webhook / health / cron。
  • worker：node dist/worker.js，long-poll SQS + 每 30s 草稿 sweep，不對外。
為何同 image？兩者共用大量程式（skills、Notion/Slack client、DynamoDB adapter）；同 image 保證版本一致、build 一次、部署一致，只用啟動指令區分角色。

入口：沿用既有 aaron-dev ALB（不自建）

不自建 ALB / ACM / Route53，而是在公司既有的 aaron-dev ALB 443 listener 上加一條 host-based rule（priority 20）：Host = notionvoice.ai-tech.ninja → 本 app 的 Target Group。TLS 憑證（*.ai-tech.ninja）、DNS 都沿用。

為什麼？帳號已有 aaron-dev ALB + 泛網域憑證 + Route53 record 指向它——自建一套 ALB/ACM/Route53 是重複投資又多一份維運。host-rule 只攔本網域，不影響 ALB 上其他服務。

網路：私有子網雙 AZ + NAT + assignPublicIp=DISABLED

Fargate task 跑在私有子網（1a + 1c 雙 AZ），無 public IP；出網（連 Bedrock us-east-1 / Transcribe / Notion / Slack / 拉 ECR）走 NAT gateway；入站一律經 ALB。

為什麼？Security Hub ECS.2 規定 task 不得有 public IP。雙 AZ 提供高可用（一個 AZ 掛了另一個頂上）。這是從最初「公有子網省 NAT」被資安通報後改過來的（見第 8 章）。

容器：readonlyRootFilesystem + ephemeral volumes

兩容器 root 檔案系統設唯讀；少數可寫需求用 task-level ephemeral volume + mountPoints 提供：

volume 名掛載點所屬容器用途
tmp-web/tmpwebNode/libc 暫存
nextcache/app/.next/cachewebNext.js ISR / fetch cache
tmp-worker/tmpworkerffmpeg / Node 暫用
為何不是 tmpfs？Security Hub ECS.5 要求唯讀根。一般直覺會用 linuxParameters.tmpfs——但那是 EC2 launch type 專屬，Fargate 不支援。Fargate 的正解是 task-level ephemeral volume（隨附 20GB）+ mountPoints。app 幾乎不寫檔（ffmpeg 純 stdin/stdout pipe），只有上表兩處需可寫。

DynamoDB：single-table（取代 6 個記憶體 store）

PK/SK 兩個字串鍵的單表設計，ttl 屬性開 TTL 自動清理。取代原本放在記憶體的 6 類狀態（詳見第 7 章 schema）。

為什麼？記憶體狀態在 task 重啟／滾動部署／多實例時會遺失或不同步 → 重複建卡、草稿按鈕失效。DynamoDB 跨容器共享、重啟不掉、on-demand 計費、TTL 自動清。

SQS 主佇列 + DLQ

web 收 webhook 後 3 秒內回 200，把慢工作（轉錄 30–120s、Notion 寫入）丟進 SQS；worker 消費。VisibilityTimeout=180（≥ 最長處理時間）、maxReceiveCount=3，重試 3 次仍失敗的毒訊息進 DLQ 隔離。

為什麼？原本 fire-and-forget：webhook 回 200 後就地跑 30–120s，部署/縮容/崩潰時正在跑的工作隨容器死掉，且 Slack 不會重送已回 200 的事件 → 該筆永久遺失。SQS 讓工作持久化、可重試、隔離毒訊息。

Amazon Transcribe streaming（語音轉文字）

worker 把 Slack 音檔轉錄成逐字稿的 pipeline（region ap-northeast-1）：

語音轉錄 pipeline
Slack 音檔m4a / ogg…
→
ffmpeg 轉碼16k mono 16-bit LPCM
→
切 chunks3200B / 100ms
→
Transcribe streaming多語言 zh-TW+en-US · pcm · +詞庫
→
取 IsPartial:false串成逐字稿
為什麼？Transcribe 專做語音轉文字、東京支援 zh-TW/en-US 串流、免 model access（只要 IAM transcribe:StartStreamTranscription）。（這是從 Nova Sonic 換來的——見第 8 章。）

多語言自動辨識（zh-TW + en-US）

預設帶 IdentifyMultipleLanguages: true + LanguageOptions: zh-TW,en-US + PreferredLanguage: zh-TW（不帶固定 LanguageCode，兩者互斥）。中文為主、夾雜英文術語或整段英文都能正確轉譯；由 TRANSCRIBE_LANGUAGE_OPTIONS 控制，設單一值則退回固定 LanguageCode。

自訂詞庫（custom vocabulary）

帶 VocabularyNames（語言辨識時為複數、per-language）＝ voice-notion-zhtw + voice-notion-enus，把成員人名／專案術語直接餵給 Transcribe 提升辨識率。

詞庫語言內容來源
voice-notion-zhtwzh-TW中文人名／部門／團隊用語（如 昌宏、產險、痛點訪談）scripts/sync-transcribe-vocabulary.ts 從 lib/vocabulary.ts + MEMBERS_JSON 自動蒐集、依中英文分流
voice-notion-enusen-US英文術語／人名（如 Notion-Voice、Databricks、Shane）
AWS 限制（script 已處理）：zh-TW 詞庫不得含拉丁字母、en-US 不得含 CJK，混合詞（如 陳采妍-Lucy）依語系拆分；詞彙僅允許字母/數字/連字號，其他字元（/、.）會被清掉。Windows 建立時中文以 \uXXXX escape 傳 --cli-input-json 避開 cp950 編碼問題。correctTranscription() 仍做繁化與變體正規化後處理。

Amazon Bedrock — Claude Opus 4.8（文字推理）

欄位解析、任務拆分、站會摘要都走 Bedrock，用 Anthropic 官方 AnthropicBedrockMantle client（Mantle 端點），認證走 task role SigV4、無 API key。三個關鍵設定各有原因（皆為第 8 章的坑收斂而來）：

設定項當前值為何這樣設
regionus-east-1東京 profile 會被 SCP 擋到大阪
model id裸前綴 anthropic.claude-opus-4-8us. inference-profile id 在 Mantle 端點 404
結構化輸出prompt 指示回 JSONMantle 此版不支援 output_config/tool_choice（回 400）

EventBridge Rule（站會排程）

經典 EventBridge Rule（非新版 Scheduler）：cron(40 1 ? * MON-FRI *)（UTC = 台北 09:40）→ 透過 API destination + Connection（帶 Authorization: Bearer <CRON_SECRET>）打 /api/cron/standup。target 設 MaximumRetryAttempts=0。

為何用 Rule 而非 Scheduler？EventBridge Scheduler 對 API destination target 的 ARN 格式驗證會失敗，經典 Rule 才穩。Rule 的 cron 是 UTC，故 40 1。cron route 是 enqueue + 立即回 200（統整走 worker），加上 retry=0，兩者共同防止「同步統整超時 → 退避重試 → 重複發訊」（見第 8 章）。

SSM Parameter Store

Notion / Slack token、CRON_SECRET、MEMBERS_JSON 等機密以 SecureString（KMS 加密）存放，task 啟動由 ECS 注入為環境變數；不進 image、不留明文。Bedrock/Transcribe 不需 key（走 task role）。

兩組 IAM 角色

Execution role：ECS agent 用——拉 ECR、寫 Logs、讀 SSM。Task role：程式碼用——DynamoDB / SQS（限本資源）、bedrock:InvokeModel + bedrock-mantle:*、transcribe:StartStreamTranscription。

6跨區設計（Cross-region）

本系統刻意把 Bedrock 放在 us-east-1、其餘全部在 ap-northeast-1。這不是偏好，是被組織 SCP 逼出來的。

服務Region原因
Bedrock（Claude Opus 4.8） us-east-1 東京區的 Opus 只能走跨區 inference profile，會路由到大阪 ap-northeast-3，被組織 SCP（p-563t3abk）明確 deny；us-east-1 的 Mantle 端點用裸前綴可直接呼叫，且 Mantle 自行處理跨區路由。
ECS / DynamoDB / SQS / Transcribe / EventBridge / ALB ap-northeast-1 主基礎設施；Transcribe 於東京支援 zh-TW 串流。

程式以 ENV.bedrockRegion（us-east-1）與 ENV.awsRegion / ENV.transcribeRegion（ap-northeast-1）分離處理。跨區的唯一代價是 worker → Bedrock 的一次美東往返延遲，對非即時的建卡流程可接受。

7程式設計原理（雲原生改造）

原始程式有兩個「單機假設」，一擴容或一重啟就會壞。整個雲原生改造就是拆掉這兩個假設：

原始假設問題本架構如何解

fire-and-forget 背景處理（webhook 回 200 後就地跑 30–120s 轉錄） 部署／縮容／崩潰時正在跑的工作隨容器死；Slack 對已回 200 的事件不重送 → 永久遺失 SQS：webhook 只入列 + 回 200，worker 消費；失敗自動重試，毒訊息進 DLQ

兩個代表性事件的完整脈絡

語音：Nova Sonic → Amazon Transcribe

Nova 2 Sonic 是 speech-to-speech（即時語音對話）模型，批次語音轉錄是逆用途。先撞 AudioOutputConfiguration must be set（Sonic 的 promptStart 必須宣告音訊輸出，即使只想轉錄），依官方 input/output-events schema 修好後 API 通了、音訊也送進去了，但三次都回 transcriptLength: 0——它不把批次錄音當作要轉錄的對象。耗費 4 個 build 週期後放棄，改用專做語音轉文字的 Amazon Transcribe（東京支援 zh-TW 串流、免 model access），複用既有 ffmpeg 產出的 16k mono LPCM。

站會：重試風暴 → enqueue + retry=0

症狀：09:40 統整完後，每隔數分鐘又重跑並重發「處理完成」。根因：cron route 同步跑完整統整（6 人 × LLM 摘要 + 寫 Notion，10–30 秒）才回 200，超過 EventBridge API destination 的 timeout（~5s）→ EventBridge 判定失敗 → 預設指數退避重試。觸發間隔 65s→104s→3.6min→6.7min→8.5min 正是退避特徵。

雙管齊下修復：止血——target 設 RetryPolicy: {MaximumRetryAttempts: 0}；治本——cron route 改「enqueue SQS + 立即回 200」，統整由 worker 背景跑（新增 kind:"standup" → runStandupAggregation），EventBridge 永遠即時收到 200。
